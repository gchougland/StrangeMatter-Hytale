# Capsule flight persistence

`LaboratoryProjectiles` persists tagged capsule shots to `capsule-flights.json`. Each entry contains a shot UUID, owner UUID, world name, position, velocity, elapsed flight time, phase, anomaly type, and the original `UUID:nonce` token. Its complete `ItemStack.CODEC` payload is stored as canonical BSON extended JSON. This preserves nested metadata and binary types, item quantity, durability, maximum durability, quality and the dropped-item animation override. Native model entities are explicitly temporary and recreated when the saved shot resumes.

The three phases are:

1. **PREPARED (survival):** write the queue entry before consuming the inventory capsule. Resolve the live native inventory section and reserve its exact expected item value atomically; stale slot snapshots cannot consume another item. Then call native `Player.saveConfig(world, store.copyEntity(ref), true)`. The projectile cannot move until this required save's future succeeds.
2. **FLIGHT:** move using the existing swept collision and gravity behavior. Checkpoint the trajectory every quarter second. On impact, `AnomalyService.release` validates and persistently clears the identity nonce before the flight is retired. Replaying an old queue file cannot release the same identity twice.
3. **REFUND:** retain the complete capsule in the queue until the owner is online and has inventory room. Reconcile an existing matching token before adding an item. A required native inventory save must succeed before the refund entry is retired. Failed saves retain the recovery phase and retry; they never silently discard the capsule.

At restart, each entry waits for its owner's inventory to become available. An older native inventory save may still contain the capsule consumed by the interrupted launch. Recovery removes copies of that exact token from the owner's backpack, storage and hotbar, forces the updated inventory save, and resumes the one queued throw. The owner can reconnect in a different world; inventory reconciliation runs on that world's thread. The saved projectile resumes when its original world and chunk are loaded. It does not force distant chunk loads.

Orderly world removal destroys only the temporary model, saves the queue, and never joins an inventory-save future on the world thread. A save that finishes after unload is reconciled on a later tick or restart using the same durable phase. This avoids a shutdown deadlock.

The active token set is concurrent, so `EquipmentService.capsuleInFlight(token)` can guard forge ingredients without acquiring the projectile service lock. A pending refund remains reserved until native inventory persistence acknowledges it. Completed forge recipes call `AnomalyService.consumeCapsule(token)` after saving their spent-capsule receipts, retiring exactly the matching contained identity. Invalid, previously released and already spent tokens cannot create fields or valid forge resources.

Blank creative template capsules and Chrono Blister shots remain ephemeral: they consume no captured identity and do not strand a paid capsule if the process stops. Creative throws of a real captured token still use the persistent queue and nonce validation. They do not change native inventory, so they enter FLIGHT directly after the queue is saved. They no longer wait for an irrelevant full player save. Restart recovery likewise resumes these creative records without consuming inventory.

`CapsuleFlightVerification` covers complete native BSON round trips, trajectory/owner/world persistence, pre-consumption and refund save acknowledgements, failed-save retries, active queue restoration, wrong/stale nonce rejection, one-time crafting consumption and preservation of a malformed user's ledger. Because native ItemStack codecs initialize Hytale logging, a standalone JVM must set `java.util.logging.manager=com.hypixel.hytale.logger.backend.HytaleLogManager` at launch. It also checks the creative/survival save-gate distinction. `NativeEquipmentVerification` checks exact-value native inventory removal, preservation of stacked payload metadata, rejection of stale delayed slot snapshots, the actual launch, moving model, native block collision and identity release, using a controlled inventory-save future in a socket-free fixture. A connected-client crash test at each save boundary remains in the acceptance checklist.

Native player saves, world entity saves and this plugin's ledger are separate storage operations. The queue and required saves close the ordinary launch, flight and refund restart gaps; they do not create a distributed transaction across all other plugins, item transfers, backups or an operating-system power failure. If an external rollback or a narrowly timed cross-container transfer restores a duplicate physical token, nonce checks still permit only one live anomaly identity, and queued/spent-token forge guards prevent replay as a crafting resource. Do not claim arbitrary cross-plugin inventory rollback is transactional.

One-shot capsule roots require a new physical click. A repeated request for an existing queue token reports its current securing-save, flight or refund phase and consumes nothing. Independent tick error handling keeps capsules progressing when another laboratory subsystem fails; native inventory-save errors are logged with their original cause while the durable recovery record remains intact.
